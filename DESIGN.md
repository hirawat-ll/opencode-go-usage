# Design notes

Working sketchbook for the panel. Short on purpose — these are the decisions
worth not undoing by accident.

## The idea

The subject is a *meter*: three budgets running down at different speeds, one of
which will bite first. So the panel is drawn like an instrument rather than a
dashboard — a dial, hairlines, digits — not three cards with progress bars.

The signature element is the **triple ring gauge**. One arc per window,
concentric, with the time horizon growing outward: 5-hour inside, month outside.
The shape encodes the data instead of decorating it, which is why it survives
being read at a glance:

- **Position is the legend.** No colour key needed — a smaller ring is always a
  shorter window.
- **The centre answers one question** — *which limit is closest?* It shows the
  highest of the three, named.
- **The legend swatches** are miniature copies of the dial with the row's own
  ring inked in, so the mapping between list and dial is learned in one look.

## Tokens

| Token | Light | Dark | Used for |
| --- | --- | --- | --- |
| `--ink` | `#16181D` | `#F3F4F6` | primary text, primary button fill |
| `--ink-2` | 58% ink | 62% ink | secondary text |
| `--ink-3` | 36% ink | 38% ink | timestamps, eyebrows, ticks |
| `--ok` | `#15754F` | `#4FC08D` | any window under 70% |
| `--warn` | `#9C5B06` | `#E0A44C` | 70–90%, or a stale read |
| `--over` | `#BD3527` | `#F0736A` | 90%+, rate limited, rejected key |
| `--track` / `--hairline` | ~10% ink | ~12% ink | empty arc, rules, borders |

Colour is spent on one meaning only: severity. Nothing else in the panel is
coloured, so an amber ring means something.

Type:

- **Numerals** — `ui-monospace` (SF Mono / Menlo), `tabular-nums`. Every number
  in the panel is monospaced, so digits do not jitter as they count and the
  columns line up. This is the panel's voice.
- **Labels** — system UI, 8.5–12.5 px. Eyebrows are uppercase at 0.12em
  tracking; everything else is sentence case.
- **Body copy** — system UI, 10.5–11 px, secondary ink.

Spacing is a 4px scale, panel padding 12/16, 11px between sections. Rows are
`5px 0` with 0.5px rules — dense, like a menu, not a landing page.

## Layout

```
bar         status dot · name                    refresh · settings
statusline  updated 12s ago · every 1m
strip       (only when something is wrong)
hero        190px dial, centre readout = biggest window
legend      swatch · name · resets-in · percent      (3 rows, hairline rules)
history     "Last 6 hours" · peak                     sparkline
foot        version                                  Quit
```

The panel measures its own height and the window follows (200–760px), so the
error strip and the empty state do not leave dead space and nothing clips.

## Motion

Two moves, both informative:

- Arc **dash offsets** transition over 680ms so a change in usage reads as a
  needle moving, not a jump.
- The centre number **counts up** from its previous value (520ms, cubic
  out) — enough to notice a change, not enough to wait for.

Everything collapses under `prefers-reduced-motion`.

## Icon

The dock icon is the same dial on a graphite superellipse (`n = 5`, sampled 3×3
per pixel) with a mint needle at the outer arc's end. The menu bar icon is the
template version of the same figure — arc, needle, hub — drawn from alpha alone
so macOS can tint it for light and dark menu bars. Both are generated by
`scripts/make-icons.mjs`, which writes PNGs directly (no image libraries) so
the art stays in the repository as code, not as an opaque binary.

## Copy

Names describe what people control: "Check for updates", "Show percentage next
to the icon", "Remove key". Failures say what happened and what to do — "Key
rejected / The API key was not accepted." with a Settings button, not "Error
401". No apology, no vagueness.

## The details view

The same dial cannot carry a breakdown, so details get a different treatment
rather than a bigger version of the dashboard: three headline numbers, then a
bar chart, then one row per model. It is the *reading* view — the panel stays
the *glance* view.

- **Headline is one number**, the thing you would ask for: tokens processed.
  Requests and estimated cost sit under it as a subordinate line, and the
  composition line (`input · output · thinking · cache read`) explains why the
  headline is as big as it is. On a real Go workload cache reads are ~98% of
  the total, and hiding that would make the number meaningless.
- **Bars, not a sparkline.** The sparkline in the panel answers "how close am I
  to the limit"; here the question is distribution over time, so the buckets are
  discrete bars. The newest bucket is inked heavier than the rest — it is
  usually still filling up, and saying so by making it look different beats
  silently under-reporting it.
- **Model rows are two lines and a rail.** The rail is the share of tokens, so
  the ranking is visible before you read a single number; the second line
  carries tokens, requests and cost. Names are shown without the provider
  prefix unless the provider is not OpenCode.
- **One scope control, above everything it affects.** The provider filter sits
  under the range control, not inside the model list it most obviously applies
  to — it changes the totals and the chart as well, and a control belongs next to
  the things it changes. When it is on, the section says so in words too.
- **Colour stays out of it.** Nothing in this view is severity-coded, because
  none of it is a limit. The only ink is the text ramp plus the bars.

The window grows to fit (200–760 px), which is what makes the larger format
possible without a second window: same panel, more room, back button where the
dashboard's title bar is.

## Workspaces

Multiple API keys exist because limits are per workspace, and percentages of two
different limits cannot be added up. The design follows from that one
constraint:

- **One at a time, never a total.** The panel shows the active workspace; no
  screen anywhere sums or averages across them.
- **A switcher only when there is something to switch.** One workspace — the
  common case — adds nothing to the panel: no row, no control. Two or more add a
  segmented control under the status line, capped at three labels with a `+N`
  escape to Settings.
- **The switcher survives the empty state.** Selecting a workspace that has no
  key shows the empty state, and the empty state keeps the switcher — otherwise
  there would be no way back without a trip through Settings.
- **Rows are the macOS list idiom**: a radio, an editable name, a masked key
  tail, and a remove button. Renaming commits on blur or Enter — no modal, no
  save button for a name.
- **Removal asks inside the row** ("Remove “Work”? · Remove / Keep") rather than
  in a dialog. The app has no dialogs to spare, and a key is not something to
  lose to a stray click.
- **The secret never crosses IPC.** The panel is sent a masked tail (`…a91f`) for
  display and nothing else; replacing a key is a write, never an edit of a value
  that was loaded. That is also why the key field is empty with a placeholder
  naming what is saved — an empty field beside a saved key would read as data
  loss.
